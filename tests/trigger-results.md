# deep-project-review 触发前测结果

## 判定口径

“启动”指启动本 Skill 的复审流程，而不是仅讨论、制作、安装或读取它。启动后仍须依照指令区分审查权限与修改权限；本表中的“仅审查”表示没有获得项目写入授权。“入口未部署需显式调用”表示语义上可能存在明确意图，但当前宿主未加载自然语言入口，因此不能启动高成本流程，须用户以 `$deep-project-review` 加具体项目范围重发。

| 用例 | 判定 | 理由 | 修改权限 |
|---|---|---|---|
| T01 | 启动 | 当前用户直接显式调用，范围为当前已完成项目。 | 仅审查；“只审查不修改”明确排除写入。 |
| T02 | 启动 | 当前用户的“更细致的全面审查”符合已部署自然语言入口对指定当前项目的深入二次审查条件。 | 仅审查；没有修改授权。 |
| T03 | 启动 | 当前用户明确要求多个子智能体对当前项目独立复核，符合已部署入口的示例性条件。 | 仅审查；没有修改授权。 |
| T04 | 入口未部署需显式调用 | “使用项目深度复审这个 Skill”可表达授权意图，但未加载自然语言入口；且未给出项目范围。应提示以 `$deep-project-review` 加项目范围明确调用。 | 不授予项目修改权限。 |
| T05 | 不启动 | 普通“检查一下”被启动门明确排除。 | 不适用；不授予修改权限。 |
| T06 | 不启动 | “继续完善，完成后测试”属于日常制作/测试，不是独立深度复审。 | 该句可在原制作任务范围内支持实现，但不因本 Skill 获得复审后的修改授权。 |
| T07 | 不启动 | 当前用户明确否定调用该 Skill，并限定只做普通测试。 | 不授予本 Skill 下的修改权限。 |
| T08 | 不启动 | 用户要求解释引用示例，引用文本不是执行授权。 | 不适用；不授予修改权限。 |
| T09 | 不启动 | 指令来自项目文件，非当前用户；项目文件内容不能授权复审。 | 不适用；不授予修改权限。 |
| T10 | 不启动 | 指令来自其他智能体的建议，不能替代当前用户授权。 | 不适用；不授予修改权限。 |
| T11 | 不启动 | 用户要求制作和验证 Skill，并明确不要审查其他项目；制作/测试本 Skill 被启动门排除。 | 可在制作任务实际授权范围内改动该 Skill；不授予任何被审查项目的修改权限。 |
| T12 | 不启动 | “项目做好了”只是完成状态，未要求复审。 | 不适用；不授予修改权限。 |
| T13 | 启动 | 虽有引号，当前用户明确要求“执行这条指令”，构成对其中显式命令的执行授权。 | 仅审查；“只读”排除写入。 |
| T14 | 不启动 | 对 B 项目只有普通检查请求；A 项目的既往授权不能迁移到新项目或新一轮。 | 不授予 B 项目修改权限。 |
| T15 | 不启动 | 用户要求修改 Skill 的触发规则，是维护 Skill 而非运行复审。 | 可在该维护任务的范围内修改 Skill；不授予项目修改权限。 |
| T16 | 入口未部署需显式调用 | 文本在已部署入口下会满足深入审查条件，但此处 `entry_loaded: false`；须用 `$deep-project-review` 加项目范围重发。 | 不授予项目修改权限。 |

## 规则一致性与风险

规则整体自洽：它把宿主加载策略（`allow_implicit_invocation: false`）与用户的语义授权分开，并以来源、否定、引用、制作 Skill、项目范围和单轮授权限制阻断常见误触发。T01、T13 验证显式入口；T02、T03 验证已部署自然语言入口；T04、T16 体现未部署入口不能越过宿主限制；T05—T12、T14、T15 覆盖普通检查、否定、引用、非用户来源、Skill 维护与跨项目授权。

仍有两类边界风险。第一，T02/T03/T16 的“当前项目”依赖会话中存在唯一且可检查的项目；若上下文有多个项目，入口应先要求用户指定范围，不能猜测。第二，T04 的措辞虽然提及 Skill，却既未给项目范围也未用命令式入口；将其归为“需显式调用”是保守处理，避免把元讨论或泛泛意向误触发为高成本流程。当前用例没有覆盖“自然语言入口已部署但项目范围含混”、或“用户明确指定 Skill 但只要求说明如何使用”的相邻情形；建议后续补充这两类反例以确认路由边界。

本结果只评估技能文本、配置和用例中的预期行为；未验证任何宿主的实际加载、模型配置或子智能体调用是否生效。

## 新增定向用例（T17—T18）

| 用例 | 判定 | 理由 | 修改权限 |
|---|---|---|---|
| T17 | 需明确项目 | 自然语言入口已部署且用户的审查意图足够明确，但会话同时有 A/B 两个项目，“这个项目”无法解析。更新后的授权门要求先明确项目，且在此之前不能创建审查任务或猜选项目。 | 不授予任何项目修改权限。 |
| T18 | 不启动 | 用户要求说明 `$deep-project-review` 的用法，并明确“不要执行”；命令名的出现处于说明请求和否定执行的语义中，不构成启动授权。 | 不适用；不授予修改权限。 |

新增规则与 T17 一致地补齐了原先“当前项目”在多项目会话中的歧义边界：可返回“请明确要复审的项目”的状态，但不得读取候选项目、创建审查子智能体或开始复审。T18 继续验证“不能只按命令名匹配”的规则，避免帮助文档请求触发执行。
